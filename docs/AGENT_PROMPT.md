## 3. Как работать

- **Порядок задач** — строго по TASKS.md: T02 → T03 → T04 → T05 → T06 → T07 → … На каждую задачу:
  1. перечитай соответствующие разделы SPEC;
  2. реализуй;
  3. выполни её «Готово, когда»;
  4. закоммить.
- **Задача закрыта** только после того, как выполнен её критерий и ты видел результат: зелёный вывод тестов, ответ curl, скриншот. «Должно работать» не считается.
- **Неоднозначности.**
  - Если спецификация чего-то не покрывает и выбор влияет на поведение для пользователя или на контракт API — **спроси пользователя** (AskUserQuestion, с рекомендуемым вариантом первым). Не выдумывай молча, пользователь это явно требует.
  - Мелкие технические решения принимай сам и записывай в раздел «Решения при реализации» в README.
- **Решения §1.1 SPEC** согласованы с заказчиком. Не меняй их без его согласия.
- **Если по ходу выясняется, что спецификация технически неверна** (API библиотеки ведёт себя иначе и т.п.):
  1. проверь по документации или исходникам;
  2. исправь реализацию;
  3. внеси правку в SPEC.md;
  4. добавь строку в REVIEW.md (раздел «Правки при реализации»);
  5. сообщи пользователю.
- **Контрольные точки** из TASKS.md соблюдай. Учёт времени веди в `docs/qa/TIMELOG.md`: задача, начало, конец, разработка или проверка. Время бери из `date` в начале и в конце задачи. Цифры нужны для README.
- **Не делай** то, что спецификация выносит за рамки (§11), и не добавляй фич сверх неё.
- **Сообщай о результатах честно.** Упавший тест, непроверенный сценарий или известный баг фиксируются в REPORT.md и README как есть.

## 5. Обязательная проверка — главное требование пользователя

Пользователь отдельно и настойчиво требует, чтобы приложение было **реально проверено**, а не только покрыто тестами.

- **T06 — проверка API через curl.** Скрипт `scripts/api-check.sh` проверяет кейсы A01–A33 из SPEC §9.3 против `npm run mock:server`. Каждое расхождение с контрактом исправляется до перехода к UI. Вывод прогона сохраняется в `docs/qa/api-check.log`.
- **T15 — интерактивная проверка UI.** Ты **сам** управляешь браузером через Playwright (скрипты на `@playwright/test`/`playwright` или Playwright MCP, если он доступен) на `npm run build && npm run preview` и проходишь **каждый** из 51 E-сценария SPEC §9.2 (E65 — P2):
  - кликаешь, вводишь с клавиатуры, переключаешь DevPanel, открываешь вторую вкладку, подменяешь время (`page.clock.setFixedTime`), готовишь данные через `/api/__dev/*`;
  - снимаешь скриншоты по таблице §9.2 в `docs/qa/screenshots/` и **открываешь каждый через Read**, чтобы посмотреть глазами: наложения, обрезанный текст, читаемость коротких броней, понятность сообщений, видимость фокуса, мобильная ширина;
  - собираешь `console` и `pageerror` — ни ошибок, ни React-warnings быть не должно;
  - каждый найденный баг исправляешь, затем проходишь сценарий заново со свежим скриншотом;
  - итог — `docs/qa/REPORT.md`: ID → ✅/❌/⚠️ → скриншот → комментарий, плюс список найденных и исправленных багов.
- **T16 — автотесты `@smoke`.** Закрепляешь ключевые сценарии в `e2e/` и прогоняешь их локально и против деплоя (T18).

**Технические детали, которые легко упустить** (всё есть в SPEC, здесь — напоминание):

- MSW-handlers исполняются **в странице**. Поэтому `page.clock` влияет и на них, а `page.route` / `setOffline` их **не перехватывают**. Ошибки симулируй через `failNext` (SPEC §5.3).
- В `playwright.config.ts` укажи `serviceWorkers: 'allow'`.
- Порядок фикстуры: `goto` → ждать `window.__mswReady` → `/api/__dev/*` → `reload`.
- TanStack Query v5 рефетчит по `visibilitychange`. В E54 событие отправляется явно.
- Для GET ставь `failNext` с `count: 2`: один повтор запроса (retry) иначе скроет ошибку.
- Запросы считай по `requestLog` из `GET /api/__dev/state`.
